# 0021. Continuous integration

Status: draft, awaiting owner review

## Context

The project's checks should run automatically on every push. The question is how the pipeline is arranged.

Facts that shaped the choice:

- The project is on GitHub and runs on Node 24. It uses ESLint and Prettier, Vitest tests and one Playwright end-to-end test ([0006](0006-testing-approach.md)), run against the production build ([0015](0015-client-build-tool.md)).
- Reviewers run the finished app with `docker compose up` ([0010](0010-how-reviewers-run-it.md)). The owner's machine has no Docker installed, so that path cannot be tried locally. GitHub's build machines have Docker.
- The task does not mention CI.
- The end-to-end test needs a browser install and can be flaky, which is why [0006](0006-testing-approach.md) names a fallback.
- No CI was ruled out because a project like this should run its checks automatically. Another CI service was ruled out because the repo is on GitHub.

## Options considered

### Option 1: one job

One GitHub Actions workflow with one job that installs, lints, typechecks, runs the tests, builds, and then runs the Playwright test.

Pros:
- The simplest workflow, in one place to read.
- One status for the whole run.

Cons:
- One serial job, so a slow or flaky end-to-end test delays the whole run.
- Nothing checks the Docker path.

### Option 2: two jobs

One workflow with two jobs running in parallel: one runs the checks, the other runs the Playwright test against the built app.

Pros:
- The checks and the end-to-end test run in parallel, so feedback is faster.
- A flaky end-to-end test does not hide the check results.

Cons:
- Both jobs need an install and a build, or an artifact shared between them.
- Nothing checks the Docker path.

### Option 3: two jobs and Docker

Option 2, plus a third job that builds the Docker image, starts it and makes a request to the page and one API route.

Pros:
- Proves the Docker path reviewers use.
- Everything in Option 2.

Cons:
- A third job and a smoke test to maintain.
- The slowest run.

### Option 4: one job plus a Docker check script

Option 1, plus a script, outside CI, that builds the image, starts it and makes the same requests. Someone with Docker runs it by hand.

Pros:
- Tests the Docker path when it is run, with no extra CI job.
- Keeps the pipeline to one job.

Cons:
- Cannot be run on the owner's machine, since there is no Docker.
- Not automatic, so it only checks the code as it was that day.
- Another script to maintain.

## Decision

Option 3: two jobs and Docker.

Two reasons decided it:

- The owner's machine has no Docker, and CI tests the Docker path without installing anything.
- With two jobs, a flaky end-to-end test does not hide the check results.

The strongest alternative is Option 2, which gives the same fast feedback and the same separation without the Docker job.

## Consequences

- One GitHub Actions workflow, run on every push and pull request, with three jobs on Node 24:
  - **Checks:** install, lint, typecheck, tests and build.
  - **End-to-end:** the Playwright test against the production build, with the browser installed in that job.
  - **Docker:** build the image, start it with the compose file, request the page and one API route, then stop it.
- A broken Dockerfile or compose file, such as a missing data file, a missing build step, a wrong port or a user without access to a file it needs, fails the Docker job before a reviewer sees it.
- The jobs fail and re-run independently, so a flaky end-to-end failure leaves the checks result visible.
- The Docker job adds run time and one more job to maintain and explain.
- The fallback in [0006](0006-testing-approach.md), an integration test in place of the end-to-end test, still applies if browser tests prove flaky or slow.
